## Statechart Explanation for the Alarm Clock

The system's behavior is managed by a **Hierarchical Finite State Machine (HFSM)** with 10 implemented states organized into a root and two main composite states: `Normal` and `Alarm`.

### 1. States and Their Meaning (10 Total)

The statechart is structured with a `Root` state containing two top-level **Composite States**: `Normal` and `Alarm`.

| Composite State | Simple State | Description |
| :--- | :--- | :--- |
| **Root** | | The parent of all states. Initial state is `Normal`. |
| **Normal** | | Encapsulates all non-alarm-related operation modes. Initial state is `Home`. |
| | `Home` | The default clock/thermometer display. The system resides here when idle. |
| | `Mode_Select` | Entered via Potentiometer movement from `Home`. Used to select the next mode (Time Set, Alarm Set, Play, or back to Home) using the Pot. |
| | `TimeSet` | Mode for the user to input the current time via serial interface. A timeout returns to `Home` after successful/invalid input. |
| | `AlarmSet` | Mode for the user to set the alarm countdown delay (5s-60s) using the Pot. |
| | `AlarmConfirmed` | A temporary state entered after setting the alarm. It starts the alarm countdown and uses a timeout to return to `Home`. |
| | `Play` | Music playback mode. The Potentiometer changes the song. |
| **Alarm** | | Encapsulates all alarm-related behavior. Initial state is `Alarm_Running`. |
| | `Alarm_Running` | The active alarm state: LED flashes, buzzer plays the alarm sound. The button press stops the alarm. |
| | `Alarm_Stopping` | Temporary state entered after a user button press, indicating the alarm is stopping. |
| | `Alarm_Stopped` | Temporary state entered after `Alarm_Stopping` or after the max alarm timeout, causing a global return to `Normal`. |

### 2. Main Events and Generation

The system responds to various events generated by hardware interactions, timers, or internal tasks.

| Event (`Evt_t`) | Description | Generation Source(s) |
| :--- | :--- | :--- |
| `EVT_BUTTON` | User presses the physical button. | `task_button` (via GPIO Interrupt) |
| `EVT_POT_MOVE` | Potentiometer knob position changes significantly. | `task_pot` |
| `EVT_TICK` | A periodic 1-second clock update signal. | `task_tick` |
| `EVT_TIMEOUT` | A software timer has expired (used for mode selection, time setting, or short confirmation screens). | `set_timeout` function in the `timeout.c` module. |
| `EVT_ALARM_TRIGGERED` | The alarm countdown expires. | `task_tick` |
| `EVT_ALARM_STOPPED` | The internal alarm sequence finishes. | Sent from state `Alarm_Stopped` to transition back to `Normal`. |

### 3. Actions Associated with States and Transitions

Actions are functions executed either upon entering/exiting a state or when a transition is taken.

| Context | Action Function | Description |
| :--- | :--- | :--- |
| **State Entry** | `display_mode_home` | Resumes `th_tick`, sets LCD to white, and displays the current time/temp. (Entry of `Home`) |
| | `show_mode_selection` | Suspends `th_tick`, starts a 5s timeout (`id1`), and displays the initial mode selection. (Entry of `Mode_Select`) |
| | `request_time_sync` | Clears the LCD, prompts for time, and **blocks using `getchar()` to synchronously wait for and parse the time input (HH:MM:SS) from the serial port By running this command in the terminal **minicom -b 115200 -o -D /dev/ttyACM0** we are able to enter the time from the keyboard**. After input is handled (valid or invalid), a timeout (`id2`) is set to return to `Home`. (Entry of `TimeSet`) |
| | `play_music` | Clears LCD, displays "PLAY," and **resumes `th_buzzer`** for music. (Entry of `Play`) |
| | `start_alarm` | **Suspends `th_tick`**, sets LCD to red, **resumes `th_led`** (flashing), **resumes `th_buzzer`** (alarm sound), and starts the 15s max alarm timeout (`id6`). (Entry of `Alarm_Running`) |
| **State Exit** | `stop_music` | **Suspends `th_buzzer`**, sets `buzzer_mode` to `BUZZ_OFF`. (Exit of `Play`) |
| | `stop_alarm` | **Suspends `th_led`** and **`th_buzzer`**, stops the alarm sound, and sets `buzzer_mode` to `BUZZ_OFF`. (Exit of `Alarm_Running` and `Alarm_Stopped`) |
| **Transition** | `update_clock_display` | Increments `current_time_seconds` and refreshes the LCD display. (Transition `Home` $\to$ `Home` on `EVT_TICK`) |
| | `update_selected_mode` | Maps the Potentiometer ADC value to one of the four modes and updates the LCD display. **Resets the mode selection timeout (`id1`)**. (Transition `Mode_Select` $\to$ `Mode_Select` on `EVT_POT_MOVE`) |
| | `update_alarm_delay` | Maps the Potentiometer ADC value to a 5s-60s delay and updates the LCD display. (Transition `AlarmSet` $\to$ `AlarmSet` on `EVT_POT_MOVE`) |
| | `update_songs` | Maps the Potentiometer ADC value to select between `BUZZ_PLAY` and `BUZZ_PLAY1` for music. (Transition `Play` $\to$ `Play` on `EVT_POT_MOVE`) |
| | (Various) | **`remove_timeout(idX)`** functions are called on transitions leaving a state that initiated a timer, ensuring the timer does not fire and send an unexpected `EVT_TIMEOUT`. |

### 4. FreeRTOS Tasks (7 Total)

The core functionality is achieved through concurrent FreeRTOS tasks, communicating with the state machine via `sm.send(Event)`.

| Task Handle | Task Name | Periodicity/Trigger | Primary Function |
| :--- | :--- | :--- | :--- |
| `th_pot` | `task_pot` | Every 100ms | Reads the Potentiometer ADC value. If change is $>50$, sends `EVT_POT_MOVE`. |
| `th_tick` | `task_tick` | Every 1000ms (1s) | Sends `EVT_TICK`. Also manages and decrements the `alarm_delay` countdown and sends `EVT_ALARM_TRIGGERED` when it reaches zero. **Suspended/Resumed by the State Machine.** |
| `th_button` | `task_button` | Event-driven (Notification) | Waits for a notification from the button interrupt. Sends `EVT_BUTTON` when pressed. |
| `th_led` | `task_led` | 500ms on/500ms off | Blinks the LED. **Suspended/Resumed by the State Machine** for the `Alarm_Running` state. |
| `th_temp` | `task_temp` | Every 4000ms (4s) | Reads the Pico's onboard temperature sensor and updates the global `current_temp`. |
| `th_serial` | `task_serial` | Every 100ms (check) | Monitors the serial input for `SYNC` or `TIME:` commands. Sends `EVT_TIME_RECEIVED` when found. |
| `th_buzzer` | `task_buzzer` | Loop (non-blocking delays) | Plays music/alarm notes based on the global `buzzer_mode` enum. **Suspended/Resumed by the State Machine.** |

### 5. Interrupt Routines

There is **one** interrupt routine dedicated to the input button:

* **Routine:** `gpio_callback`
* **Trigger:** `GPIO_IRQ_EDGE_RISE` (Button press) on `BUTTON_PIN` (D18).
* **Communication:** Instead of directly calling `sm.send()`, which is unsafe in an ISR, the routine uses **FreeRTOS Task Notification** (`vTaskNotifyGiveFromISR`) to wake up the blocked `th_button` task. `th_button` then safely executes `sm.send(EVT_BUTTON)`.

### 6. Problems Encountered and Solutions Implemented

#### A. Display Functionality Limitation

**Problem:** The standard LCD library provided only basic character printing (`lcd_print` at the current cursor position), making it cumbersome to reliably display a string on the second line (row 1) without manually managing the cursor position for every character and handling string termination.

**Solution:** The helper function `lcd_print_line2(const char *text)` was created to reliably write a string to the second line of the 16x2 LCD.

* **How it works:** The function iterates through the input string (`text`), and for each character, it explicitly calls `lcd_set_cursor(1, i)` to position the cursor on the second row (`1`) at the correct column (`i`). It then prints the single character using `lcd_char()`. This guarantees the string starts at the first column of the second line and only prints valid characters.

#### B. Managing Multiple Concurrent Timers

**Problem:** Several states (`Mode_Select`, `TimeSet`, `AlarmConfirmed`, `Alarm_Running`) require distinct, short-lived software timeouts, but using a single timer source is complex. Furthermore, a timeout must be canceled if a user action transitions the state machine before the timer expires.

**Solution:** **Using Unique Timeout IDs and Removal Logic.**

* The `set_timeout` function returns a unique integer ID (`id1`, `id2`, etc.).
* Critical actions and transitions that override the timer explicitly call `remove_timeout(idX)` and reset the ID to `-1`. This ensures that a transition triggered by a user action is not immediately followed by a stale `EVT_TIMEOUT` event from an old state, thereby maintaining control over the state flow.

#### C. Controlling the Buzzer's Behavior

**Problem:** The single physical buzzer component needs to perform multiple, distinct behaviors: silence, different music patterns during the `Play` state, and a specific, high-priority alarm pattern during the `Alarm_Running` state. The behavior must change immediately when the state machine commands it.

**Solution:** **Buzzer Mode State Machine (within a Task).**

* A global `volatile BuzzerMode buzzer_mode` enum was created with states: `BUZZ_OFF`, `BUZZ_PLAY`, `BUZZ_PLAY1`, and `BUZZ_ALARM`.
* The `task_buzzer` runs an infinite loop containing a **switch statement** based on this `buzzer_mode`.
* **State machine actions** (e.g., `play_music` or `start_alarm`) simply change the value of `buzzer_mode` and resume the task.
* The `task_buzzer` loop constantly checks this variable and executes the corresponding, complex note sequence (or idles in `BUZZ_OFF`). This delegates the repetitive task of note generation to a dedicated logic block within the task, simplifying the main statechart's job to just setting a control variable.
